## Overview

`process_lines` accepted three of the nine `EDGE_WEIGHT_FORMAT` layouts TSPLIB defines —
`FULL_MATRIX`, `UPPER_ROW`, `LOWER_DIAG_ROW` — and returned
`Unsupported EDGE_WEIGHT_FORMAT` for the rest. The corpus only exercises one of the six missing
ones, but it exercises it three times: `si175`, `si535` and `si1032` are `UPPER_DIAG_ROW`, and all
three were unreadable by the CLI, the API and the WASM alike.

The parser's error was already the right shape — it refuses rather than guesses — so this was a
missing feature rather than a silent-wrong-answer bug. It still had a visible cost: the bench tier
substitutes `gr120` for `si175` (see `bench/matrix/tier-a.toml`), and those three problem pages
offered an "Open in Solver" button that could not work.

## Goals

- Read all nine layouts, with the shared reader keeping the mapping explicit and reviewable.
- Keep the failure modes the existing reader had: a wrong token count and an unknown format are
  errors, never a silently different matrix.
- Verify the new layouts against data with a known answer, not just against a fixture.

## What was not in scope

`EDGE_WEIGHT_TYPE` is a different list, and the unsupported types there (`MAN_2D`, `MAX_2D`,
`EUC_3D`, `XRAY1`, …) stay unsupported. There is a deliberate test asserting that a declared but
unhonoured type is an error rather than a silent EUC_2D measurement
(`test_process_lines_rejects_an_unsupported_declared_type`), and no corpus instance declares any of
them — adding them would need the 3-D variants to carry a third coordinate in `KDPoint`.

## Implementation

- `explicit_entries(format, n)` returns the `(i, j)` pairs a layout stores, in file order, for all
  nine layouts. One table, so the triangle, the diagonal and the row/column order each appear once.
- `parse_explicit(tokens, n, format)` checks the token count against that table, mirrors the stored
  triangle into a full matrix (TSPLIB `TYPE: TSP` is symmetric; `ATSP` is rejected before this
  point), and packs the lower triangle row-wise — the single shape `DistanceMatrix` reads.
- The three per-format readers were replaced by these two. Six unit tests that called them directly
  became table-driven cases over all nine layouts.
- A section with no `EDGE_WEIGHT_FORMAT` now says so, instead of reporting an unsupported format
  named `""`; the declared format is upper-cased before dispatch.

## Acceptance Criteria

- [x] All nine layouts parse; `si175`, `si535` and `si1032` load in the CLI.
- [x] A wrong token count is an error for every layout, and an unknown format names itself.
- [x] The three previously-supported layouts behave identically (423 lib tests pass, including the

- [x] `cargo fmt --check` and `cargo clippy --workspace -- -D warnings` are clean.

## Verification

The strong check is external: eight EXPLICIT instances ship a *real* optimal tour (`bayg29`,
`bays29`, `brg180`, `fri26`, `gr24`, `gr48`, `gr120`, `pa561` — the other 54 `.opt.tour` files in
`data/tsplib` are 7-line stubs). Each was re-encoded into every one of the nine layouts and its
published optimal tour scored under the result via `--optimal-tour`:

- **72 runs, 0 mismatches** — every layout, on every instance, scored the tour at exactly the
  published optimum (1610, 2020, 1950, 937, 1272, 5046, 6942, 2763).
- **The check is sensitive**: declaring UPPER_COL's tokens as UPPER_ROW scores `gr48`'s tour at
  19712 instead of 5046, so a transposed mapping cannot pass it.
- `si175`/`si535`/`si1032` declare exactly `n(n+1)/2` tokens and every diagonal-offset value is 0,
  which is what a diagonal-inclusive layout must contain — a non-diagonal file read as one would
  show real distances at those offsets.

Not verified: the browser path end to end. `teeline-wasm` calls `teeline::tsp::tsplib::read_from_str`
(the function containing the dispatch), so the fix is included by construction, but the transpiled
WASM in `js-bindings` is only regenerated by the release/deploy flow and `jco` could not be
installed here (read-only npm cache, no network). The deployed `/solve/` page picks this up with the
next WASM rebuild, not before.

## Follow-ups

- The tier still substitutes `gr120` for `si175`. Now that `si175` parses, it *could* enter the
  tier, but changing an instance invalidates comparability with the published shards — a
  `tasks/bench-tier-a-campaign` decision, not this one.
- `scripts/gen-problem-pages.mjs` reads the same formats in JS for the problem pages. It handles
  five of the nine (the four the corpus uses, plus `LOWER_ROW`); the remaining four layouts would
  make the two readers agree completely. It fails loudly on an unknown layout, so this is a
  consistency gap rather than a silent one.
- The three `si*` pages still offer "Open in Solver" with no published `.opt.tour` to overlay
  ([[tasks/ship-missing-optimal-tours]] owns the missing tours).
