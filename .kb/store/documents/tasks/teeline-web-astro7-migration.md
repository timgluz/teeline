## Overview

teeline-web (tspsolver.com) is a hand-rolled Vite 8 MPA: 31 build entries (4 hand-authored HTML pages, 17-18 generated algorithm-doc pages, 10 Preact "explainer" island pages), a WASM solver worker, and a growing custom Vite plugin stack that exists mainly to work around Vite MPA's lack of a server-rendering story — notably `ssr-nav-html`, built specifically because Googlebot's non-JS crawl saw zero internal links between algorithm pages when nav was client-injected only.

The user wants to add a blog. Brainstorming surfaced that this is also the right moment to retire the custom plugin stack in favor of Astro 7's native server rendering, file-based routing, and content collections. Full design/rationale is in the approved plan: `/home/timgluz/.claude/plans/cosmic-chasing-curry.md` (also summarized below).

## Goals

- Migrate teeline-web from Vite 8 MPA to Astro 7, in-place, single big-bang branch.
- Unify the 17-18 existing algorithm doc pages and a new blog onto one Astro content-collections pipeline (retiring `build-docs.mjs`, the Eta template, manual sitemap generation).
- Retire `ssr-nav-html` and the client/server dual-render nav pattern in favor of Astro's native server rendering.
- Keep the 10 Preact explainer islands as-is (`@astrojs/preact`, `client:visible`) — rewriting them to vanilla JS is an explicit phase-2 follow-up, out of scope here.
- Preserve WASM worker integration (jco bindings, preview2-shim, worker.ts) with zero behavioral change.
- Preserve/improve SEO: sitemap coverage, no CLS regression (past incident: commit `dde6dc0`, CLS 0.67 from deferred CSS on homepage — do not repeat).
- Ship an RSS feed for the new blog.

## Context

Full design detail (architecture, astro.config.mjs shape, content-collection schemas, route-by-route conversion plan, dependency changes, risks, suggested phase ordering) lives in the approved plan file: `/home/timgluz/.claude/plans/cosmic-chasing-curry.md`. Key decisions locked in during brainstorming:

- **Full migration, not blog-bolt-on**: driven by wanting to also kill the SSR-nav hacks and simplify the islands architecture, not just enable a blog.
- **Big-bang, single branch**: 31 routes is small enough that incremental dual-stack adds more complexity than it saves.
- **Blog content**: plain Markdown, no MDX, `src/content/blog/`.
- **Explainers stay Preact for now**: rewriting the 10 stateful components (PSO/GSA/tabu/GA/CS/FPA/LK/SA/SOM/Fourier) to vanilla JS is a separate phase-2 effort, scoped later — not part of this task.
- **stochastic-hill.md**: include as an 18th doc page now (currently fully orphaned — no nav entry, no generated page).
- **api-key page**: include in the new auto-generated sitemap (its absence today looks like an oversight in the old manual `sitemapUrls` array).
- **RSS feed**: include now via `@astrojs/rss`.

Two corrections surfaced during research beyond the original architecture survey:
- `htmx.org` is a fully dead dependency (zero usages found via grep; only a stale comment in `main.ts` references it).
- `topbar.ts`'s dropdown close-on-outside-click listener is real interactivity (not just SSR-duplicated markup) and must survive as a `<script>` in `Topbar.astro`.

**Phase-0 go/no-go risk** (do this first): Astro 7 ships a Rolldown-backed Vite 8. Must confirm early that `@sentry/vite-plugin` and the custom `force-preview2-shim-browser` resolver plugin still hook correctly under Astro's plugin ordering, and that the WASM worker loads and `solve()` returns a result end-to-end. If this doesn't work, the rest of the plan is moot.

Suggested phase ordering (see plan file for full detail): (1) spike/validate WASM+Astro compat, (2) scaffold+config, (3) content collections + frontmatter codemod, (4) static content pages, (5) doc pages, (6) home/app page WASM wiring, (7) explainer islands, (8) nav/SEO parity + RSS, (9) testing, (10) CI/CD, (11) cutover.
